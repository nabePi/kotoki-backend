# Kotoki Backend — M10 Hardening & Operasi Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Backend Kotoki siap produksi: manifest Kubernetes (kustomize), image & pipeline deploy, observability (collector, dashboard, alert), pemeriksaan keamanan/privasi otomatis, harness load test + gate G1–G4b/soak/real, failure injection F1–F16, validasi kapasitas, runbook dan checklist produksi; semua yang butuh cluster/vendor nyata ditandai **MANUAL GATE** dengan perintah dan kriteria lulus.
**Architecture:** Semua artefak operasi berada di luar paket fitur: `deploy/` (YAML + skrip assert), `test/load` (generator, verifier, gate, kapasitas), `test/chaos` (skenario + driver), `test/tools` (dashgen, metricref, readinesscheck). Harness hanya memakai `internal/kotokiclient` (M5) dan tidak mengimpor paket fitur. Manifest divalidasi tanpa cluster (`kustomize build` → `kubeconform` → skrip assert berbasis `yq` → test Go yang me-render overlay dan menjalankan `config.Load*`); gate load tidak boleh lulus "kosong" (data hilang = gagal).
**Tech Stack:** kustomize, kubeconform, promtool, yq v4, actionlint (alat dev, versi dipin di `deploy/k8s/hack/tools.env`); Go stdlib + `go-redis` + `pgx` (verify/chaos) + `coder/websocket` via `kotokiclient`; **tanpa library YAML baru** (YAML dibaca lewat `yq -o=json`); GitHub Actions; Envoy Gateway, KEDA, ESO, cert-manager, kube-prometheus-stack, Chaos Mesh (di cluster).
**Spec:** docs/superpowers/specs/2026-10-12-kotoki-backend-design.md — §13.1, §13.5–13.14, §14.12.2, §15.2 (menutup butir yang menunggu pengukuran), D-NEW-13-*.
**Master plan:** docs/superpowers/plans/2026-10-13-kotoki-backend-00-master.md (Global Constraints di sana berlaku untuk semua task)
**Depends on:** M1 (`Makefile` §14.10.4, `ci.yml`, empat Dockerfile, `docker-compose.yml` + profil observability, `config.LoadAPI/LoadRealtime/LoadWorker`, `metrics`, `test/arch`), M5 (`kotokiclient`: `Client`, `RunConversation`, `Step`, `Report`; harness `test/e2e`), M6 (`worker run-job`, metrik §9.7.9, `balance.Service.Reconcile`, job akun purge), M7/M8 (consumer evaluation/memory/learner untuk K13), M9 (`deploy/config/provider.env` rekomendasi sakelar/model, adapter real untuk gate Real). **M10 memperluas, bukan menggandakan, artefak M1/M6.**

Grace worker = `WORKER_SHUTDOWN_GRACE` + 10.
- Semua Deployment: `maxSurge 25%`, `maxUnavailable 0`; topologySpread zone (`maxSkew 1`, `DoNotSchedule`) + hostname (`ScheduleAnyway`); `runAsUser 65532`, `runAsNonRoot`, `readOnlyRootFilesystem`, `allowPrivilegeEscalation:false`, `drop: [ALL]`, `seccomp RuntimeDefault`, `automountServiceAccountToken:false`, `/tmp` emptyDir 64Mi; `preStop sleep 5`; probes ke port `ops` 9090: startup `/healthz` 2s×30, liveness `/healthz` 10s/2s/3, readiness `/readyz` 5s/2s/2; priorityClass realtime `kotoki-realtime-high`, lainnya `kotoki-default`; PDB `maxUnavailable: 1` semua.
- Realtime: `terminationGracePeriodSeconds 40` = preStop 5 + `DRAIN_SAFEPOINT_TIMEOUT 20s` + `DRAIN_FLUSH_TIMEOUT 5s` + margin 10; `REALTIME_READY_MAX_SESSIONS 95 ≤ REALTIME_MAX_SESSIONS 100 ≤ REALTIME_HARD_MAX_SESSIONS 120`; nodeSelector `kotoki.io/pool: realtime` + toleration `workload=realtime:NoSchedule`.
- KEDA: realtime `sum(kotoki_realtime_sessions_active{namespace="kotoki"})` threshold `70`, min 3, max 20, fallback `failureThreshold 3` → 15 replika, trigger cpu 70, scaleUp stab 0 (+4 pods / +100% per 60 s, `Max`), scaleDown stab 600 (−1 per 300 s); api cpu 65% (stab 300 s); evaluation `evaluation.session_completed` 5/pod (2–8); memory `memory.session_completed` 10/pod (1–4); learner `learner.evaluation_completed` 20/pod (1–3); worker-core tanpa autoscale.
- Gateway: dua host `api.kotoki.id` (`/api/v1` → `kotoki-api:8080`) dan `realtime.kotoki.id` (hanya `/api/v1/realtime` → `kotoki-realtime:8081`; staging `*.staging.kotoki.id`); `/api/v1/realtime` → `kotoki-realtime:8081`, `HTTPRoute timeouts.request: 0s`, idle 120 s, consistent-hash cookie `kotoki_rt` TTL 3600 s, tanpa max connection duration; `/api/v1` → `kotoki-api:8080` request 30 s, idle 120 s; TLS ≥ 1.2, HTTP→301, HSTS `max-age=31536000; includeSubDomains`; L4 LB idle ≥ 350 s.
- Collector: tail sampling 100% status error, 100% durasi > 2 s, 10% sisanya; Loki retensi 30 hari (app), 400 hari (`audit="true"`).
- Gate (§13.12.3): G1 100 CCU 5m/30m; G2 250 5m/30m; G3 500 10m/30m; G4a 1000 15m/60m (HPA off, 10 pod, `REALTIME_READY_MAX_SESSIONS=101`); G4b 1000 15m/60m; Soak 500 10m/4h; Real 20 2m/15m. Knob fake: `FAKE_PRIMARY_STT_LATENCY_MS=250`, `FAKE_PRIMARY_LLM_LATENCY_MS=500`, `FAKE_LLM_TOKEN_INTERVAL_MS=30`, `FAKE_PRIMARY_TTS_LATENCY_MS=300`.
- Kriteria: K1 turn P95 ≤ 1,5 s; K2 overhead P95 ≤ 150 ms; K3 bargein-stop P95 ≤ 150 ms; K4 client barge-in P95 ≤ 600 ms; K5 REST P95 ≤ 200 ms & `POST /sessions` ≤ 300 ms; K6 WS connect ≥ 99,9%; K7 `SERVER_ERROR` ≤ 0,1%; K8 resume ≥ 99%; K9 slow_consumer = protocol_violations = 0; K10 CPU & mem < 80% limit, 0 restart; K11 acquire-wait P99 < 50 ms, PG CPU < 60%; K12 Redis CPU < 50%, 0 error; K13 outbox lag P99 < 5 s, evaluasi ≤ 5 m, DLQ 0; K14 verify 0 pelanggaran; K15 drift RSS/goroutine < 10%.
- Perilaku VU (§13.12.2): durasi 300/600/900 = 60/30/10%; `USER_FIRST`/`AI_FIRST` 50/50; think 1–3 s; barge-in 10% (1,0–2,0 s setelah frame AI pertama); filler 15%; disconnect 2% (reconnect 1–5 s); akhir 70% `DURATION_ELAPSED` / 30% `session.end`; instance ≤ 500 VU.
- Fault key Redis `kotoki:fake:faults`, entri `"<CAP>.<INSTANCE>"` UPPERCASE (`FAKE_PRIMARY`/`FAKE_FALLBACK`), `mode` ∈ `error|timeout|slow|fail_after_first_audio|disconnect_mid_stream`; skenario chaos: load 100 CCU, inject T+5 m, revert T+15 m, lalu verify.
